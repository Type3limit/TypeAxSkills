# AI Dev Rule

让项目获得 AI 的实现速度，同时保留人类对系统演化的理解、决策权和维护责任。把 AI 视为作者或顾问，而不是可以为合并结果负责的维护者。

## 选择工作模式

- **制定规则**：根据团队规模、项目风险和现有流程，提出最小可执行制度。
- **仓库审计**：只读检查现状并列出证据、缺口和优先级；除非用户同时要求修改，否则不要写文件。
- **落地门禁**：用户明确要求实施时，修改现有规范、自动化检查、所有权或模板，并运行与风险相称的验证。
- **评审变更**：评估一个计划或变更集是否满足行为、边界、证据、兼容性和恢复要求。

做制度设计或项目审计时，读取 [references/quality-framework.md](references/quality-framework.md)。需要生成规则文档、变更说明、变更模板或评审清单时，再读取 [references/templates.md](references/templates.md)。若用户询问当前开源项目政策，使用官方一手资料重新核实，不要假设参考文件中的外部规则永远不变。

## 技术中立原则

不要预设语言、框架、版本控制系统、托管平台、依赖管理器、测试框架、自动化平台、部署方式或团队规模。先识别项目实际采用的机制，再把通用原则映射过去。

本文中的“变更集”可对应 patch、commit、PR、MR、CL 或其他审阅单位；“集成目标”可对应主干、发布分支、制品候选或其他权威状态；“自动化门禁”可由 CI、构建服务器、本地钩子、制品验证器或项目已有系统实现。示例工具名只用于帮助理解，不构成要求。

## 工作流程

### 1. 先理解项目，而不是直接铺设模板

按任务需要检查现有的贡献说明、AI/agent 指令、架构文档、所有权映射、构建与依赖定义、验证入口、自动化流程、发布流程和运行方式。不存在某类机制时不要强行引入；优先沿用项目已有术语和载体。

区分三类情况：

- 已存在且有效的机制；
- 明确缺失的机制；
- 因证据不足而无法确认的机制。

不要把未检查到误写成不存在。运行验证时尽量先建立基线，避免把原有失败归因于当前改动。

### 2. 先确定行为与风险

对非平凡改动要求说明：

- 要解决的问题、预期行为和不变量；
- 明确不做什么；
- 受影响模块、接口、数据和用户；
- 方案、替代方案与主要取舍；
- 验证方法、上线方式和回滚路径；
- 能长期解释和维护该变更的人类 owner。

风险由最高风险因素决定，而不是由改动行数决定。涉及鉴权、支付、数据删除、不可逆迁移、公共 API、并发、构建发布链或广泛兼容性的改动，提高评审和验证等级。具体分级见质量框架。

### 3. 保持变更可推理

- 一个变更只承担一个连贯目的。
- 功能修改与大范围重构分开；格式化和机械改写也应与行为变化分开。
- 优先删除被替代的旧路径，避免两套实现长期并存。
- 变更过大时按行为、边界或迁移阶段拆分；不要只为满足行数阈值机械切碎。
- 拒绝无现实调用方的“未来可能需要”抽象。

文本行数只能作为某些代码项目的辅助信号，不是通用质量结论。优先判断一个不了解实现过程的维护者能否在合理时间内理解目的、完整影响面和恢复办法。生成内容、可验证的机械迁移、数据或模型变更和大规模删除应按真实审阅成本单独判断。

### 4. 要求证据，而不是接受“应该没问题”

根据风险选择单元、集成、端到端、兼容性、迁移、性能、并发、故障恢复或安全验证。行为修复尽可能提供一个旧实现会失败、新实现会通过的测试。

禁止为了让自动化结果变绿而：

- 删除或放宽仍然有效的断言；
- 吞掉异常或添加静默 fallback；
- 跳过测试、扩大忽略列表或降低门禁；
- 改变需求却不更新契约和说明。

测试覆盖率是寻找盲区的信号，不是单独的质量目标。测试本身也要检查是否真正能在实现损坏时失败。

### 5. 把所有权和合并控制分开

- AI 不得批准自己的改动，AI 审查只能提供建议。
- 中高风险变更必须由理解相关模块的人类 owner 决定是否接受。
- 让正确的人评审正确的边界；跨模块变更应邀请所有受影响领域。
- 保护权威集成目标并要求必要检查。条件允许时，对真正准备进入该目标的候选状态重新验证，而不是只相信较早的分支或局部结果。
- 合并者或明确 owner 负责处理合并后的回归，包括及时修复或回滚。

不要把项目知识只写进面向 AI 的指令。架构、验证和发布规则首先应有人类可读的权威来源；具体 agent 的指令文件只应摘要并链接该来源。

### 6. 让发布和维护成为质量闭环

高风险变化应具备适合项目形态的反馈信号、分阶段采用方式和可执行恢复路径。发现有意义的回归时，优先恢复权威版本或用户环境健康，再从容修复并补回归验证。

定期处理高变更频率与高复杂度同时出现的热点、重复实现、失效兼容层、无人维护区域和 flaky tests。不要把“以后重构”当作合并当前混乱的默认理由。

## 输出要求

先给结论，再给证据和行动。审计结果应包含：

1. 当前已经具备的保护；
2. 按严重度排序的缺口；
3. 每个缺口对应的仓库证据或“尚未验证”说明；
4. 最小可行修复与后续增强项；
5. 哪些决策仍必须由项目负责人作出。

实施后说明修改的文件、启用的门禁、实际运行的验证及剩余风险。不要声称任何流程能保证零缺陷，也不要让制度复杂度超过项目实际风险和维护能力。

## 始终避免

- 未查看项目便批量生成平台专用所有权文件、自动化配置、决策记录或规则文件；
- 用第二个 AI 的赞同代替人类责任；
- 把 lint、覆盖率或静态分析分数当作维护性的充分证明；
- 为了“架构整洁”进行未获授权的大规模重写；
- 引入没有 owner、测试、升级策略或退出方案的新依赖；
- 将普通开发问题都升级为重型治理流程。
